How the demos work, and what to say about them

Two demos run from one server on this board: the Live VLM main demo and the traffic monitoring cascade. Everything runs on the board; nothing goes to the cloud.

Before you start

  • Start the demo with the desktop icon VLM Demo + Cascade. It opens the main demo at https://localhost:8090 (accept the self-signed certificate once).
  • Power mode is MAXN with clocks locked: the launcher does this once per boot and may ask for the sudo password.
  • The VLM is qwen3-vl:4b-instruct on the GPU: check with ollama ps (should show 100% GPU). The first answer after a pause of more than 30 minutes takes a few extra seconds while the model loads.
  • The USB webcam (Trust Full HD, /dev/video0) is the default video source. Only one program can use it at a time.
  • The stats panel shows a live GPU % and a GPU clock. If it is stuck at 0%, see Troubleshooting.
  • Free RAM: free -h should show around 12 GB or more available. The GPU shares the 32 GB, so every loaded model counts.
  • No other test or benchmark servers are running; Hermes is off; system updates are frozen until after the event.

Main demo: Live VLM

How it works

  1. Camera feed: the server reads the USB camera (or GMSL / RTSP / a video file) and streams it to the page over WebRTC.
  2. Frame sampling: every 30th frame (about one per second) is shrunk to at most 1024 px and sent as a JPEG.
  3. Prompt: a preset (Scene, Objects, Safety, Retail, Navigation, …) or your own text, plus an answer-length limit.
  4. Qwen3-VL-4B on the Ampere GPU looks at the frame and writes the answer. One frame at a time: frames that arrive while it is busy are skipped.
  5. Answer streams into the VLM Output panel word by word, with TTFT, speed and latency, plus CPU / RAM / GPU / temperature stats below.

What the numbers on screen mean

  • TTFT (time to first token): from sending the frame until the first word arrives. Mostly image processing ("prefill").
  • Speed (tok/s): how fast the model writes once it has started. Limited by memory bandwidth.
  • Tokens: length of the last answer. Latency: the whole answer, end to end. Avg / Count: running average and number of answers.
  • AI Accelerators: the GPU ring (load and clock, 930 MHz max) runs the VLM. The DLA ring is the Orin's NPU-style engine: it shows 0% "free for vision models" in the main demo, and moves ("traffic detector") when you start detection on the traffic page with the default NPU detector. Talking point: the IQ9 runs everything on its one NPU; the Orin runs the VLM on the GPU and still has two DLAs free.
  • Thermal: CPU, GPU and SoC temperatures.
  • The chip button in the header opens the Platform panel: AFE-R750 datasheet, live board stats, module power, and the AI stack.

Cascade demo: traffic monitoring

How to run it

  1. In the main demo, click the car button. The highway video starts playing.
  2. Press Start Detection. Boxes appear on vehicles, and each new vehicle gets a card on the right.
  3. Click a vehicle card, then Describe: the VLM reads color, type, brand and, if readable, the plate from the vehicle's best crop.
  4. Open the settings drawer (gear) to switch the detector between NPU (DLA), GPU and CPU live, or to change the VLM.
  5. The house button goes back to the main demo.

Why a cascade

A small, fast detector looks at every frame; the large VLM only looks at the vehicles you ask about. That keeps the VLM's seconds per answer out of the video loop, and lets each model run on the engine that suits it: the detector on the DLA, the VLM on the GPU.

Detector option (settings)Runs onPer frameVideo with detection
YOLOv8n · NPU (DLA 0) defaultDLA via TensorRT FP16; detection head on the GPU~25 ms~23 fps
YOLOv8n · GPUAmpere GPU via TensorRT FP16~9 ms~30 fps

YOLO26n · NPU / GPU / CPUthe IQ9's detector, same three options~33 / 9.5 / 63 ms~20 / 30 / 16 fps
  • Why YOLOv8n is the default: on the highway video it finds the same vehicles as YOLO26n (1.39 vs 1.44 per frame) and is ~25% faster on the DLA.
  • Why not 100% on the DLA: both models produce 8,400 candidate boxes, over the DLA's 8,192 limit, so the final detection layers run on the GPU; the backbone and neck run on the DLA.
  • Why the GPU is faster here: the model is tiny (~3 ms of GPU time). The DLA's value is taking the detector off the GPU so the GPU stays free for the VLM, at lower power.
  • Describe settings: up to 120 tokens; prompt "Describe this vehicle in 1-2 sentences: its color, type (car/truck/bus/etc.), and brand if visible. Only mention the license plate if it is clearly legible"; editable with the Prompt button. One description at a time.
  • Only vehicles are reported (car, truck, bus, motorcycle); confidence threshold 0.45.

Troubleshooting

GPU % stuck at 0 (while the model is clearly working)

The stats lost their connection to the jtop service. The demo reconnects by itself within ~5 seconds; if it doesn't, restart the demo: VLM Demo (Stop), then VLM Demo + Cascade. Check the real value with jtop or tegrastats.

Answers are slow, or the board feels sluggish

Check memory with free -h and loaded models with ollama ps. Only qwen3-vl:4b-instruct should be loaded. Unload others with ollama stop <model>. The first answer after 30 minutes idle is slower while the model loads.

Traffic video stutters

Switch the detector to YOLOv8n · GPU in the traffic settings (full 30 fps). The DLA default runs at ~23 fps.

No camera image in the main demo

Check the Video Source panel is on Webcam with the Trust Full HD Webcam selected. Close any other program using the camera (Cheese, another browser tab). v4l2-ctl --list-devices lists the cameras.

Firefox says it is already running

Run pkill firefox and start the demo again. Firefox is a snap; snap updates are on hold, so it won't change before the event.

The page doesn't load

Check the server: tail -f ~/live-vlm-webui-cascade/run.log. Restart with the desktop icons. Accept the certificate warning at https://localhost:8090.

jtop                      # live CPU / GPU / power / temperatures
tegrastats                # the same from NVIDIA, one line per second
nvpmodel -q               # power mode (should say MAXN)
ollama ps                 # loaded model, should be qwen3-vl:4b-instruct, 100% GPU
free -h                   # RAM; the GPU shares it
tail -f ~/live-vlm-webui-cascade/run.log   # demo server log

After the event

  • Turn updates back on with sudo snap refresh --unhold, but keep snapd held: snapd 2.77 breaks every snap on this kernel.
  • Turn the Hermes agent back on: systemctl --user enable --now hermes-gateway.
